## 1. Blacklisting and Whitelisting

### What are Blacklisting and Whitelisting?

Blacklisting and whitelisting are two **access control methodologies** used to determine what is allowed or denied within a system, network, or application. They represent opposite philosophical approaches to security.

### Blacklisting (Default Allow)

**Definition:** Everything is allowed **except** items explicitly listed as bad.

```
┌─────────────────────────────────────────────┐
│            BLACKLISTING MODEL              │
├─────────────────────────────────────────────┤
│                                             │
│   ┌─────────┐      ┌─────────┐             │
│   │ ALLOW   │      │  DENY   │             │
│   │─────────│      │─────────│             │
│   │ All     │      │ Malware │             │
│   │ software│      │ domains │             │
│   │ All IPs │      │ Known   │             │
│   │ All     │      │ bad IPs │             │
│   │ users   │      │ Blocked │             │
│   │         │      │ keywords│             │
│   └─────────┘      └─────────┘             │
│                                             │
│   "Innocent until proven guilty"           │
└─────────────────────────────────────────────┘
```

**Examples of Blacklisting:**
- Antivirus software (blocks known malware signatures)
- Email spam filters (blocks known spam senders)
- Web proxies (blocks known malicious URLs)
- IDS/IPS signatures (blocks known attack patterns)

**Advantages:**
- Low administrative overhead for normal operations
- Users have freedom to access most resources
- Easy to implement and understand

**Disadvantages:**
- **Cannot block unknown threats** (zero-day attacks)
- Requires constant updates to stay effective
- Attackers can easily change hashes, domains, IPs

### Whitelisting (Default Deny)

**Definition:** Everything is denied **except** items explicitly listed as allowed.

```
┌─────────────────────────────────────────────┐
│            WHITELISTING MODEL              │
├─────────────────────────────────────────────┤
│                                             │
│   ┌─────────┐      ┌─────────┐             │
│   │ ALLOW   │      │  DENY   │             │
│   │─────────│      │─────────│             │
│   │ Approved│      │ All     │             │
│   │ software│      │ other   │             │
│   │ Approved│      │ software│             │
│   │ IPs     │      │ All other│             │
│   │ Approved│      │ IPs     │             │
│   │ users   │      │ All other│             │
│   │         │      │ users   │             │
│   └─────────┘      └─────────┘             │
│                                             │
│   "Guilty until proven innocent"           │
└─────────────────────────────────────────────┘
```

**Examples of Whitelisting:**
- Application control (only approved executables can run)
- Network firewall (only allow specific ports/protocols)
- Outbound web filtering (only allow specific approved websites)
- USB device control (only approved USB devices)

**Advantages:**
- **Blocks unknown threats** (zero-day attacks cannot run)
- Much stronger security posture
- No dependency on signature updates

**Disadvantages:**
- High administrative overhead (must approve everything)
- Can break business operations if too restrictive
- Requires continuous maintenance as needs change

### Comparison Table

| Aspect | Blacklisting | Whitelisting |
|--------|--------------|---------------|
| Default stance | Allow | Deny |
| Security level | Low to Moderate | High |
| Administrative effort | Low | High |
| Zero-day protection | No | Yes |
| User impact | Low | High (can be frustrating) |
| Update requirements | Constant (signatures) | Moderate (new approvals) |
| Best use case | General purpose, low-risk | High-security, controlled environments |

### Hybrid Approach

Most organizations use a **hybrid model**:
- **Whitelist** for critical systems (servers, payment terminals, executive workstations)
- **Blacklist** for general user workstations
- **Greylist** – Temporary block for suspicious items pending analysis

### Real-World Examples

| Use Case | Method | Why |
|----------|--------|-----|
| Corporate workstations | Hybrid (blacklist + application whitelist) | Balance security and productivity |
| Industrial control systems (ICS) | Strict whitelisting | Critical infrastructure, no tolerance for malware |
| Email security | Primarily blacklisting + greylisting | Too many legitimate senders to whitelist |
| Child safety software | Whitelisting (only approved websites) | Strict control over content |

## 2. Anti-Malware Solutions

### What is Anti-Malware?

Anti-malware (antivirus) software is designed to **detect, prevent, and remove malicious software** including viruses, worms, trojans, ransomware, spyware, adware, and rootkits.

### Evolution of Anti-Malware

| Generation | Era | Technology |
|------------|-----|-------------|
| 1st Gen | 1980s-90s | Signature-based (virus definitions) |
| 2nd Gen | Late 1990s | Heuristic analysis (behavior patterns) |
| 3rd Gen | 2000s | Real-time protection, on-access scanning |
| 4th Gen | 2010s | Cloud-based, machine learning, sandboxing |
| 5th Gen | Present | NGAV (Next-Gen AV), EDR integration, behavioral AI |

### Detection Methods

| Method | How it Works | Strengths | Weaknesses |
|--------|--------------|-----------|-------------|
| **Signature-based** | Matches file hashes or code patterns against a database | Fast, accurate for known malware | Misses zero-days, polymorphic malware |
| **Heuristic-based** | Analyzes code structure and behavior patterns | Can detect modified/unknown variants | Higher false positives |
| **Behavioral-based** | Monitors runtime actions (file changes, registry, network) | Detects malware after execution | Requires execution first |
| **Sandboxing** | Executes suspicious files in isolated environment | Deep analysis, sees full behavior | Resource intensive, can be detected by malware |
| **Machine Learning** | Trained models on millions of malware samples | Detects novel malware without signatures | Requires large training data, can be fooled |

### Types of Anti-Malware Deployments

| Type | Description | Best For |
|------|-------------|----------|
| **Endpoint AV** | Installed on workstations and servers | All endpoints |
| **Network AV** | Scans traffic at gateway or email server | Perimeter defense |
| **Cloud AV** | Lightweight agent + cloud analysis | Remote workers, low-resource devices |
| **Mobile AV** | Smartphone and tablet protection | BYOD environments |

### Next-Generation Antivirus (NGAV)

NGAV replaces traditional signature-based AV with:

```
┌─────────────────────────────────────────────────────────┐
│                    NGAV CAPABILITIES                    │
├─────────────────────────────────────────────────────────┤
│  ✓ Machine learning detection                          │
│  ✓ Behavioral analysis                                 │
│  ✓ Process ancestry tracking                           │
│  ✓ Memory protection (buffer overflow, ROP)            │
│  ✓ Script analysis (PowerShell, JavaScript)            │
│  ✓ Fileless malware detection                          │
│  ✓ Cloud-based threat intelligence                     │
│  ✓ Integration with EDR/SIEM                           │
└─────────────────────────────────────────────────────────┘
```

### Anti-Malware Best Practices

1. **Keep definitions updated** – Automatically, hourly if possible
2. **Enable real-time protection** – Not just scheduled scans
3. **Configure regular full scans** – Weekly minimum
4. **Enable cloud-delivered protection** – Faster response to new threats
5. **Set up alerting** – Notify SOC on detections
6. **Test regularly** – Use EICAR test file
7. **Have a remediation process** – What happens after detection?

### Common Anti-Malware Products

| Category | Products |
|----------|----------|
| Enterprise | CrowdStrike, SentinelOne, Carbon Black, Microsoft Defender for Endpoint |
| Consumer | Malwarebytes, Bitdefender, Kaspersky, Norton |
| Open Source | ClamAV |

## 3. Honeypots and Honeynets

### What is a Honeypot?

A **honeypot** is a decoy system or resource designed to **attract, deceive, and monitor attackers**. It appears as a legitimate, vulnerable target but is actually isolated and closely observed.

### Core Concept

```
                    ┌─────────────────────────────────────┐
                    │          PRODUCTION NETWORK          │
                    │  ┌─────┐ ┌─────┐ ┌─────┐            │
                    │  │Web  │ │ DB  │ │ App │            │
                    │  │Server│ │Server│ │Server│            │
                    │  └─────┘ └─────┘ └─────┘            │
                    │         ▲                            │
                    │         │ Firewall                   │
                    │         │                            │
                    │  ┌──────┴──────────────────┐         │
                    │  │      HONEYNET ZONE      │         │
                    │  │  ┌─────┐ ┌─────┐       │         │
                    │  │  │Honey│ │Honey│       │         │
                    │  │  │Pot 1│ │Pot 2│       │         │
                    │  │  └─────┘ └─────┘       │         │
                    │  │  ┌─────┐ ┌─────┐       │         │
                    │  │  │Honey│ │Honey│       │         │
                    │  │  │Pot 3│ │Pot 4│       │         │
                    │  │  └─────┘ └─────┘       │         │
                    │  └────────────────────────┘         │
                    └─────────────────────────────────────┘
```

### Types of Honeypots by Interaction Level

| Type | Interaction Level | Description | Use Case |
|------|------------------|-------------|----------|
| **Low-interaction** | Minimal | Emulates services (e.g., fake SSH, fake HTTP). Easy to deploy. | Basic attack detection, scanning |
| **Medium-interaction** | Moderate | Simulates more complex services, some attacker interaction | Attack pattern analysis |
| **High-interaction** | Full | Real OS and services, attacker can fully interact | Deep forensic analysis, research |

### Types of Honeypots by Purpose

| Type | Purpose |
|------|---------|
| **Production Honeypot** | Detect real attacks on the network (placed inside corporate network) |
| **Research Honeypot** | Study attacker behavior, discover new threats (academic, security firms) |
| **Spam Honeypot** | Catch email spammers (open relay simulation) |
| **Database Honeypot** | Detect SQL injection and database attacks |
| **Web Honeypot** | Catch web application attacks (fake login pages, admin panels) |

### What is a Honeynet?

A **honeynet** is a network of multiple honeypots, designed to simulate an entire network segment or infrastructure.

```
┌─────────────────────────────────────────────────────────┐
│                      HONEYNET                           │
│                                                         │
│   ┌──────────┐    ┌──────────┐    ┌──────────┐        │
│   │  Honeypot │    │  Honeypot │    │  Honeypot │        │
│   │  (Web)    │    │  (DB)     │    │  (File)   │        │
│   └──────────┘    └──────────┘    └──────────┘        │
│         │               │               │              │
│         └───────────────┼───────────────┘              │
│                         │                              │
│                  ┌──────────────┐                      │
│                  │ Honey Router │ ← Traffic logging    │
│                  │ (Honeywall)  │ ← Activity capture   │
│                  └──────────────┘                      │
│                         │                              │
│                         │ (Isolated)                   │
│                    ┌────────┐                          │
│                    │ Sensor │ → SIEM                   │
│                    └────────┘                          │
└─────────────────────────────────────────────────────────┘
```

### Information Collected from Honeypots

| Data Type | What It Reveals |
|-----------|-----------------|
| Source IP | Attacker origin |
| Attack vectors | Which vulnerabilities targeted |
| Tools used | Malware, exploits, scanners |
| Commands executed | Attacker objectives (data theft, persistence, lateral movement) |
| Time of attack | Attack patterns (day/night, weekends) |
| Dwell time | How long attacker stays |

### Legal & Ethical Considerations

| Consideration | Implication |
|---------------|-------------|
| **Entrapment** | Honeypots are generally legal (passive deception, not coercion) |
| **Liability** | Honeypot should not attack back or cause damage to attacker systems |
| **Privacy** | Must not capture legitimate user data (only unauthorized access) |
| **Disclosure** | Some jurisdictions require notice of monitoring |

### Honeypot Tools

| Tool | Type | Description |
|------|------|-------------|
| **Honeyd** | Low-interaction | Open source, emulates multiple OS/services |
| **Cowrie** | Medium-interaction | SSH/Telnet honeypot |
| **Dionaea** | Medium-interaction | Captures malware via protocol emulation |
| **T-Pot** | All-in-one | Honeypot platform (multiple honeypots + ELK) |
| **Modern Honey Network** | Research | Distributed honeypot network |

## 4. Firewalls

### What is a Firewall?

A **firewall** is a network security device that **monitors and filters incoming and outgoing network traffic** based on predetermined security rules. It establishes a barrier between trusted internal networks and untrusted external networks (like the internet).

### Basic Firewall Logic

```
                    ┌─────────────────────────────────────────┐
                    │              FIREWALL                   │
                    │                                         │
   INTERNET ────────┤  ┌─────────────────────────────────┐   ├──────── TRUSTED NETWORK
   (Untrusted)      │  │         RULE SET                 │   │    (Trusted)
                    │  │                                 │   │
                    │  │  Allow: HTTP (80), HTTPS (443)  │   │
                    │  │  Allow: Established connections │   │
                    │  │  Deny:  All other inbound       │   │
                    │  │  Allow: All outbound            │   │
                    │  └─────────────────────────────────┘   │
                    └─────────────────────────────────────────┘
```

### Types of Firewalls

| Type | Layer (OSI) | How it Works | Pros | Cons |
|------|-------------|--------------|------|------|
| **Packet Filtering** | 3 (Network) | Inspects headers (IP, port, protocol) | Fast, simple | No application awareness, no state |
| **Stateful Inspection** | 3 & 4 (Network/Transport) | Tracks connection state (TCP handshake) | Remembers context, more secure | More resource intensive |
| **Application/Proxy Firewall** | 7 (Application) | Inspects actual data payload (HTTP, FTP, DNS) | Deep inspection, content filtering | Slower, more complex |
| **Next-Generation (NGFW)** | 3-7 | Packet filter + stateful + App ID + IPS + User ID | Full visibility, integrated security | Expensive |
| **Cloud Firewall** | Virtual | Firewall as a service (FWaaS) | Scalable, no hardware | Dependency on cloud provider |

### Firewall Deployment Architectures

| Architecture | Description | Diagram Concept |
|--------------|-------------|-----------------|
| **Screened Host** | Single firewall with router | Internet → Router/Firewall → Internal |
| **Dual-homed** | Firewall with two network interfaces | Internal ↔ Firewall ↔ Internet |
| **DMZ (Demilitarized Zone)** | Public-facing servers in isolated segment | Internal ← Firewall → DMZ → Internet |
| **Multi-tier** | Multiple firewalls for defense in depth | Internet → External FW → DMZ → Internal FW → Internal |

### DMZ Architecture (Most Common)

```
                    INTERNET
                        │
                        ▼
              ┌─────────────────┐
              │  Edge Firewall  │
              │  (External)     │
              └────────┬────────┘
                       │
            ┌──────────┼──────────┐
            │          │          │
            ▼          ▼          ▼
      ┌─────────┐ ┌─────────┐ ┌─────────┐
      │ Public  │ │  Mail   │ │  Web    │
      │ DNS     │ │ Server  │ │ Server  │
      └─────────┘ └─────────┘ └─────────┘
            │          │          │
            └──────────┼──────────┘
                       │
              ┌────────┴────────┐
              │ Internal Firewall│
              │ (Trusted)        │
              └────────┬────────┘
                       │
              ┌────────┴────────┐
              │  Internal LAN   │
              │  (Workstations, │
              │   Servers)      │
              └─────────────────┘
```

### Firewall Rule Structure

**Typical Rule Components:**

| Component | Example |
|-----------|---------|
| Source IP | 192.168.1.0/24 |
| Source Port | ANY |
| Destination IP | 203.0.113.10 |
| Destination Port | 443 (HTTPS) |
| Protocol | TCP |
| Action | ALLOW / DENY |
| Logging | Yes/No |

**Rule Order Matters:** Firewalls process rules from **top to bottom** – first match wins.

### Sample Firewall Rules (Corporate)

| Order | Source | Dest IP | Dest Port | Protocol | Action | Reason |
|-------|--------|---------|-----------|----------|--------|--------|
| 1 | ANY | Mail Server | 25 | TCP | ALLOW | Inbound email |
| 2 | ANY | Web Server | 80,443 | TCP | ALLOW | Web traffic |
| 3 | Internal | ANY | 53 | UDP | ALLOW | DNS outbound |
| 4 | Internal | ANY | 80,443 | TCP | ALLOW | Web browsing |
| 5 | ANY | Internal | ANY | ANY | DENY | Block inbound to internal |
| 6 | ANY | ANY | ANY | ANY | DENY | Default deny |

### Firewall Best Practices

1. **Default deny** – Block everything unless explicitly allowed
2. **Least privilege** – Only allow required ports/protocols
3. **Regular rule reviews** – Remove stale or overly permissive rules
4. **Logging** – Enable logging on deny rules and critical allow rules
5. **Change management** – Document all rule changes
6. **Segment traffic** – Separate user, server, and DMZ zones
7. **Implement application inspection** on NGFW

### Popular Firewall Products

| Category | Products |
|----------|----------|
| Enterprise NGFW | Palo Alto, Fortinet, Check Point, Cisco Firepower |
| Small Business | Sophos, SonicWall, WatchGuard |
| Open Source | pfSense, OPNsense, iptables (Linux), Windows Firewall |
| Cloud Native | AWS Security Groups, Azure NSG, Google Cloud Firewall |

## 5. Logging and Monitoring

### What is Logging?

**Logging** is the systematic recording of events, transactions, and activities that occur within systems, applications, and networks. Logs are the **raw material** of security monitoring.

### What is Monitoring?

**Monitoring** is the active, real-time (or near real-time) observation and analysis of logs, metrics, and alerts to **detect security incidents, operational issues, and compliance violations**.

### Relationship Between Logging and Monitoring

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│   EVENT     │ →  │    LOG      │ →  │  MONITOR    │ →  │   ALERT     │
│ (Something  │    │ (Recorded   │    │ (Analyzed   │    │ (Notification│
│  happens)   │    │  entry)     │    │  in SIEM)   │    │  to analyst) │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
```

### Types of Logs

| Log Type | Source | Examples |
|----------|--------|----------|
| **Operating System** | Windows Event Log, syslog | Logon events, process creation, service changes |
| **Application** | Web server, database, app logs | Apache access/error logs, SQL Server logs |
| **Security** | Firewall, IDS/IPS, AV | Blocked connections, detected threats |
| **Authentication** | Domain controller, RADIUS, VPN | Successful/failed logins, MFA events |
| **Network** | Routers, switches, netflow | Traffic volumes, session data, BGP changes |
| **Cloud** | AWS CloudTrail, Azure Monitor | API calls, resource changes, IAM activity |
| **Endpoint** | EDR, Sysmon | Process trees, file changes, registry modifications |

### Critical Log Fields (Every Log Should Have)

| Field | Description | Example |
|-------|-------------|---------|
| **Timestamp** | When the event occurred (UTC preferred) | 2025-01-15T14:32:11Z |
| **Source** | Which system generated the log | WEB-SRV-01 |
| **Event ID/Type** | What happened | Event ID 4625 (Failed logon) |
| **User/Account** | Who performed the action | jsmith |
| **Source IP** | Where the request came from | 203.0.113.45 |
| **Destination/Resource** | Target of the action | FILE-SRV-02 |
| **Result/Status** | Success or failure | Failure |

```
                    ┌─────────────────────────────────────────┐
                    │            CENTRALIZED SIEM             │
                    │  ┌─────────────────────────────────┐   │
                    │  │     Log Storage & Indexing       │   │
                    │  └─────────────────────────────────┘   │
                    │  ┌─────────────────────────────────┐   │
                    │  │     Correlation Engine           │   │
                    │  └─────────────────────────────────┘   │
                    │  ┌─────────────────────────────────┐   │
                    │  │     Alerting & Dashboard         │   │
                    │  └─────────────────────────────────┘   │
                    └──────────────▲──────────────────────────┘
                                   │
          ┌────────────┬───────────┼───────────┬────────────┐
          │            │           │           │            │
          ▼            ▼           ▼           ▼            ▼
    ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
    │Windows  │  │ Linux   │  │Firewall │  │Web      │  │ Database│
    │Servers  │  │Servers  │  │Logs     │  │Server   │  │Logs     │
    │(EventLog│  │(syslog) │  │         │  │Logs     │  │         │
    └─────────┘  └─────────┘  └─────────┘  └─────────┘  └─────────┘
```

### Log Management Best Practices

| Practice | Recommendation |
|----------|----------------|
| **Retention period** | Minimum 1 year (regulatory may require more: 3-7 years) |
| **Time synchronization** | All systems must use NTP (same timezone, ideally UTC) |
| **Log integrity** | Use write-once storage, hashing, or tamper-proof logs |
| **Secure transmission** | Use TLS, encrypted channels (syslog-TLS) |
| **Log rotation** | Prevent disk full (daily or size-based rotation) |
| **Access control** | Restrict log access to authorized personnel only |

### What to Monitor (Priorities)

| Priority | Type | Examples |
|----------|------|----------|
| **Critical** | Security events | Failed logins, privilege escalations, malware detections |
| **High** | Access changes | New admin accounts, permission changes, group modifications |
| **Medium** | System changes | Service restarts, software installs, config changes |
| **Low** | Informational | Routine access, scheduled tasks, normal activity |

### Common Monitoring Use Cases

| Use Case | Query Logic |
|----------|-------------|
| Brute force detection | >10 failed logins from same IP in 5 minutes |
| Unusual login time | Successful login at 3 AM from non-shift user |
| Impossible travel | Login from NYC then London within 1 hour |
| Data exfiltration | Large outbound data transfer (>100MB) |
| Privilege escalation | Admin group membership change |
| Malware beaconing | Repeated connections to suspicious domain |

## 6. Patch Management

### What is Patch Management?

**Patch management** is the systematic process of identifying, acquiring, testing, and deploying software updates (patches) to fix **security vulnerabilities**, bugs, and performance issues.

### Why Patch Management Matters

| Statistic | Implication |
|-----------|-------------|
| 60%+ of breaches | Involve unpatched vulnerabilities |
| Zero-day to exploit | Average 7 days after public disclosure |
| Unpatched systems | Remain vulnerable for months or years |
| Ransomware | Often exploits known, unpatched vulnerabilities (EternalBlue, Log4j) |

### The Patch Management Lifecycle

```
┌─────────────────────────────────────────────────────────────────────┐
│                    PATCH MANAGEMENT LIFECYCLE                       │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│   │ IDENTIFY │ →  │  TEST    │ →  │ APPROVE  │ →  │  DEPLOY  │ →  │  VERIFY  │
│   │ (Find    │    │ (Lab/    │    │ (Risk    │    │ (Push to │    │ (Confirm │
│   │ patches) │    │  staging)│    │  review) │    │ systems) │    │  success)│
│   └──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
│        │                                                               │
│        └───────────────────────────────────────────────────────────────┘
│                                    │
│                              ┌──────────┐
│                              │ REPORT   │
│                              │ (Metrics,│
│                              │  missing)│
│                              └──────────┘
└─────────────────────────────────────────────────────────────────────┘
```

### Types of Patches

| Type | Description | Example |
|------|-------------|---------|
| **Security Patch** | Fixes a vulnerability | CVE-2021-44228 (Log4Shell) |
| **Critical Update** | Fixes a critical bug | Blue Screen of Death fix |
| **Feature Update** | Adds functionality | Windows 10 22H2 |
| **Service Pack** | Collection of patches | Windows SP1 |
| **Hotfix** | Urgent, single-issue patch | Emergency out-of-band fix |
| **Cumulative Update** | All previous patches bundled | Monthly Windows Update |

### Patch Management Process in Detail

#### 1. Identification
- Subscribe to vendor security bulletins (Microsoft, Linux, Cisco)
- Monitor CVE databases (NVD, CISA Known Exploited Vulnerabilities)
- Use vulnerability scanners (Nessus, Qualys, OpenVAS)

#### 2. Testing
- Deploy patches to non-production environment first
- Test critical applications for compatibility
- Document any issues or conflicts

#### 3. Approval
- Risk assessment: CVSS score, exploit availability, asset criticality
- Change management approval (for production)
- Schedule deployment window

#### 4. Deployment
- Use automated tools (WSUS, SCCM, Ivanti, ManageEngine)
- Phased rollout: Pilot → Ring 1 (low risk) → Ring 2 → All
- Emergency/out-of-band for critical vulnerabilities

#### 5. Verification
- Confirm patch is installed (scan or report)
- Verify system functionality
- Remediate any failed patches

### Patching Challenges & Solutions

| Challenge | Solution |
|-----------|----------|
| **Downtime requirements** | Use high-availability clusters, maintenance windows |
| **Application compatibility** | Thorough testing, vendor communication, rollback plan |
| **Remote/offline devices** | Cloud-based patch management, VPN connectivity |
| **Legacy systems** | Virtual patching (WAF), network isolation |
| **Zero-day exploits** | Emergency out-of-band patching, compensating controls |
| **Patch fatigue** | Prioritize critical/exploited vulnerabilities only |

### Prioritization Frameworks

| Framework | Logic |
|-----------|-------|
| **CVSS Score** | 9.0-10 = Critical (patch within 24-48 hrs) |
| **CISA KEV** | Known Exploited Vulnerabilities (patch within 2 weeks) |
| **Asset Criticality** | Patch internet-facing servers before internal workstations |
| **Exploit Availability** | Public exploit code = higher priority |

### Sample Patch Schedule

| Priority | Response Time | Example |
|----------|---------------|---------|
| **Emergency** | Within 4 hours | Active zero-day exploitation in the wild |
| **Critical** | Within 48 hours | CVSS 9+, no known exploit yet |
| **High** | Within 2 weeks | CVSS 7-8.9 |

## 7. IDS and IPS Concepts

### What are IDS and IPS?

| Term | Full Name | Function |
|------|-----------|----------|
| **IDS** | Intrusion Detection System | **Detects** and **alerts** on malicious activity (passive) |
| **IPS** | Intrusion Prevention System | **Detects** and **blocks** malicious activity (active) |

### IDS vs IPS: The Critical Difference

```
                    ┌─────────────────────────────────────────────┐
                    │                    IDS                       │
                    │                                             │
                    │   Malicious Traffic ──► IDS ──► Alert       │
                    │         │                                   │
                    │         ▼                                   │
                    │   Allowed to pass ──► Destination           │
                    │                                             │
                    │   "Detect and report" (Passive)             │
                    └─────────────────────────────────────────────┘

                    ┌─────────────────────────────────────────────┐
                    │                    IPS                       │
                    │                                             │
                    │   Malicious Traffic ──► IPS ──► BLOCK       │
                    │         │                    │              │
                    │         ▼                    ▼              │
                    │   Blocked/Dropped      Alert to SOC         │
                    │                                             │
                    │   "Detect and block" (Inline/Active)        │
                    └─────────────────────────────────────────────┘
```

### IDS/IPS Deployment Locations

| Location | Purpose |
|----------|---------|
| **Network Perimeter** | Detect external attacks (between internet and firewall) |
| **Internal Network** | Detect lateral movement (between internal segments) |
| **DMZ** | Monitor public-facing servers |
| **Server Farm** | Protect critical servers |
| **Cloud** | Virtual IDS/IPS for cloud workloads |

### IDS/IPS Architecture

```
                    ┌─────────────────────────────────────────────┐
                    │         IDS/IPS ARCHITECTURE                │
                    ├─────────────────────────────────────────────┤
                    │                                             │
                    │   Network Traffic ──► Packet Capture        │
                    │                           │                 │
                    │                           ▼                 │
                    │                    ┌──────────────┐         │
                    │                    │  Protocol    │         │
                    │                    │  Decoder     │         │
                    │                    └──────┬───────┘         │
                    │                           │                 │
                    │                           ▼                 │
                    │                    ┌──────────────┐         │
                    │                    │  Detection   │         │
                    │                    │  Engine      │         │
                    │                    └──────┬───────┘         │
                    │                           │                 │
                    │         ┌─────────────────┼─────────────────┐
                    │         │                 │                 │
                    │         ▼                 ▼                 ▼
                    │   ┌──────────┐    ┌──────────┐    ┌──────────┐
                    │   │Signature │    │Anomaly   │    │Behavioral│
                    │   │Detection │    │Detection │    │Analysis  │
                    │   └──────────┘    └──────────┘    └──────────┘
                    │         │                 │                 │
                    │         └─────────────────┼─────────────────┘
                    │                           │
                    │                           ▼
                    │                    ┌──────────────┐
                    │                    │  Alert/Log   │
                    │                    │  (IDS) or    │
                    │                    │  Block (IPS) │
                    │                    └──────────────┘
                    └─────────────────────────────────────────────┘
```

### Detection Methods

| Method | How it Works | IDS/IPS | Strengths | Weaknesses |
|--------|--------------|---------|-----------|-------------|
| **Signature-based** | Matches known attack patterns (snort rules) | Both | Low false positives, fast | Misses zero-days, requires updates |
| **Anomaly-based** | Compares traffic to baseline (statistical deviation) | Both | Detects unknown attacks | High false positives, needs training |
| **Protocol Analysis** | Verifies protocol compliance (RFC violations) | Both | Detects protocol abuse | Protocol-specific |
| **Behavioral** | Analyzes sequence of events (multi-stage attacks) | Advanced | Detects complex attacks | Resource intensive |

### Common Detection Signatures (Snort Example)

```
# Detect SQL Injection attempt
alert tcp $HOME_NET any -> $HTTP_SERVERS $HTTP_PORTS
(msg:"SQL Injection - Union Select";
 flow:to_server,established;
 content:"union"; nocase;
 content:"select"; nocase;
 pcre:"/union\s+select/i";
 sid:1000001; rev:1;)

# Detect NMAP XMAS scan
alert tcp $EXTERNAL_NET any -> $HOME_NET any
(msg:"NMAP XMAS Scan detected";
 flags:FPU;
 threshold:type both, track by_src, count 1, seconds 60;
 sid:1000002; rev:1;)
```

### Response Actions (IPS)

| Action | Description |
|--------|-------------|
| **Alert** | Generate notification |
| **Drop/Block** | Discard the malicious packet |
| **Reset** | Send TCP RST to terminate connection |
| **Reject** | Send ICMP unreachable or TCP reset |
| **Log** | Record full packet for analysis |
| **Inline Bypass** | Temporarily disable inspection (fail-open) |

### False Positives vs False Negatives

```
                    ┌─────────────────────────────────────────────┐
                    │         DETECTION ACCURACY MATRIX           │
                    ├─────────────────────────────────────────────┤
                    │                                             │
                    │                 ACTUAL                       │
                    │            Attack      Benign               │
                    │          ────────     ────────              │
                    │   Alert  │  True     │  False    │          │
                    │          │ Positive  │ Positive  │          │
                    │   ──────────────────────────────────         │
                    │   No     │  False    │  True     │          │
                    │   Alert  │ Negative  │ Negative  │          │
                    │                                             │
                    │   False Positive = Wasted analyst time      │
                    │   False Negative = MISSED ATTACK (bad)      │
                    └─────────────────────────────────────────────┘
```

### Tuning IDS/IPS (Reducing False Positives)

| Technique | Description |
|-----------|-------------|
| **Whitelisting** | Exclude trusted IPs, subnets |
| **Threshold tuning** | Adjust sensitivity (counts, time windows) |
| **Protocol decoders** | Ensure correct protocol parsing |
| **Passive mode first** | Run IDS mode before enabling IPS |
| **Regular review** | Analyze alerts, disable noisy rules |

### IDS/IPS Placement Strategy

| Architecture | Description |
|--------------|-------------|
| **Inline (IPS only)** | Device sits directly in traffic path, blocks in real-time |
| **Tap/SPAN (IDS)** | Device listens to mirrored port, cannot block |
| **Hybrid** | IPS at perimeter (block known bad), IDS internally (detect lateral movement) |

### Popular IDS/IPS Products

| Category | Products |
|----------|----------|
| **Open Source** | Snort, Suricata, Zeek (formerly Bro) |
| **Enterprise NGFW** | Palo Alto (built-in IPS), Fortinet, Check Point |
| **Dedicated IPS** | Cisco Firepower, Trend Micro TippingPoint |
| **Cloud** | AWS GuardDuty, Azure IDS (with open source), GCP Cloud IDS |

### IDS/IPS vs NGFW (Clarification)

| Feature | Traditional Firewall | IDS/IPS | Next-Gen Firewall |
|---------|---------------------|---------|-------------------|
| Port/protocol filtering | Yes | No | Yes |
| Application identification | No | Partial | Yes |
| Intrusion detection | No | Yes | Yes |
| Intrusion prevention | No | Partial (NGFW includes IPS) | Yes |
| SSL/TLS inspection | No | Partial | Yes |

> **Note:** Most modern NGFWs include built-in IPS functionality.
