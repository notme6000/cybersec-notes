## 1. Data Leak Prevention (DLP)

### What is DLP?

**Data Loss Prevention (DLP)** is a set of tools and processes designed to **detect and prevent unauthorized transmission, use, or exfiltration of sensitive data**—whether accidental or malicious.

### Core Objective

> *"Ensure that sensitive data does not leave the organization's control."*

### The Three States of Data (DLP Coverage)

| State | Description | DLP Focus |
|-------|-------------|-----------|
| **Data at Rest** | Stored on servers, databases, endpoints, cloud storage | Scanning, classification, encryption |
| **Data in Motion** | Transmitted across networks (email, web, FTP, APIs) | Monitoring, blocking, inspection |
| **Data in Use** | Actively being processed (opened, edited, copied) | Application control, clipboard monitoring |

### Why DLP is Critical

| Threat | Example |
|--------|---------|
| **Accidental exposure** | Employee emails a spreadsheet with SSNs to wrong recipient |
| **Malicious insider** | Employee copies customer database to USB drive before leaving |
| **Compromised account** | Attacker exfiltrates data via legitimate user credentials |
| **Third-party risk** | Vendor accesses more data than permitted |
| **Compliance violation** | Unencrypted PII leaving network violates GDPR/HIPAA/PCI DSS |

### DLP Detection Methods

| Method | How it Works | Example |
|--------|--------------|---------|
| **Regex Pattern Matching** | Searches for specific patterns | Social Security Number: `\d{3}-\d{2}-\d{4}` |
| **Fingerprinting** | Creates unique hash of sensitive documents | Confidential contract (any copy detected) |
| **Keyword Matching** | Looks for specific terms | "Confidential", "Internal Use Only", "NDA" |
| **Exact Data Matching (EDM)** | Compares against database of known sensitive values | Customer credit card numbers from CRM |
| **File Type Detection** | Identifies files by magic numbers/headers | Detects .docx, .xlsx, .pdf even if renamed |
| **Optical Character Recognition (OCR)** | Reads text from images | Scanned document containing "Confidential" |
| **Machine Learning** | Learns what "normal" data looks like | Flags unusual data volumes or formats |

### DLP Response Actions

| Action | Description | Typical Use |
|--------|-------------|-------------|
| **Block** | Prevent transmission entirely | High-risk data to external domains |
| **Quarantine** | Hold for review by security team | Suspicious but not certain |
| **Encrypt** | Automatically encrypt the data | Email with sensitive attachments |
| **Alert** | Notify SOC or data owner | Policy violation tracking |
| **Log** | Record event for audit | Compliance reporting |
| **Notify User** | Inform user of policy violation | Accidental exposure prevention |
| **TLS Enforcement** | Require encrypted channel | Preventing cleartext transmission |

### DLP Policy Example (High-Level)

| Policy Name | Rule | Condition | Action |
|-------------|------|-----------|--------|
| **PII Protection** | Credit card numbers (Luhn check) | Outbound email | Block + Alert |
| **Source Code Protection** | Contains "© Company" and source file extension | Upload to personal cloud | Block + Alert + Notify user |
| **Healthcare Data** | Contains "Patient" and 10-digit MRN | External USB copy | Quarantine + Alert |
| **Executive Protection** | Sender = CEO or CFO | Any outbound attachment | Allow + Always log |
| **Confidential Marking** | Contains "CONFIDENTIAL" watermark | External recipient | Encrypt + Alert |

### DLP Challenges

| Challenge | Mitigation |
|-----------|-------------|
| **False positives** | Fine-tune rules, use confidence scoring, machine learning |
| **Performance impact** | Use content inspection only for high-risk channels |
| **Encrypted traffic** | Use TLS decryption (with legal approval) |
| **Insider evasion** | Monitor user behavior, combine with UEBA |
| **Cloud complexity** | Use CASB (Cloud Access Security Broker) with DLP |
| **Privacy concerns** | Implement data masking, clear policies, legal review |

### Popular DLP Products

| Category | Products |
|----------|----------|
| **Enterprise** | Symantec DLP, Forcepoint, Digital Guardian, McAfee DLP |
| **Cloud-Native** | Microsoft Purview (formerly MIP), Netskope, Proofpoint, Gmail DLP |
| **Open Source** | OpenDLP, MyDLP (limited functionality) |
| **Integrated** | Many EDR/XDR platforms include basic DLP |

## 2. Introduction to SIEM

### What is SIEM?

**Security Information and Event Management (SIEM)** is a comprehensive solution that provides **real-time analysis, correlation, and management** of security alerts and events generated by applications, systems, and network hardware.

### SIEM Combines Two Technologies

| Component | Function |
|-----------|----------|
| **SIM (Security Information Management)** | Long-term storage, reporting, compliance, forensic analysis |
| **SEM (Security Event Management)** | Real-time monitoring, correlation, alerting |

### Correlation (The "Magic" of SIEM)

**Correlation** is the process of connecting individual events across time and sources to identify a security incident.

**Example Correlation Rule:**

> "If a user has 5 failed login attempts (Windows Event 4625) followed by a successful login (Event 4624) from a different country within 10 minutes → Create HIGH alert: Possible credential compromise"

### Normalization (Making Sense of Different Logs)

Different devices log the same information differently:

| Raw Log Source | Original Format | Normalized Field |
|----------------|-----------------|------------------|
| Windows | EventID 4624 | event_type = "Successful Login" |
| Linux (SSH) | "Accepted password for root from 10.0.0.1" | event_type = "Successful Login" |
| Cisco ASA | "%ASA-6-302013: Built outbound TCP connection" | event_type = "Connection Established" |

SIEM normalizes all to a **common schema** (e.g., same field names: `src_ip`, `dest_ip`, `user`, `action`).

### SIEM Use Cases

| Use Case | Example Rule |
|----------|--------------|
| **Brute Force Detection** | >10 failed logins from same source IP in 5 min |
| **Privilege Escalation** | User added to Domain Admins outside normal hours |
| **Lateral Movement** | Same user logs into 3+ workstations in 2 minutes |
| **Data Exfiltration** | >100MB outbound traffic from database server |
| **Impossible Travel** | Login from NY and London within 1 hour |
| **Malware Beaconing** | Endpoint connects to known C2 domain every 60 seconds |
| **Account Sharing** | Same user session active on two different workstations |

### SIEM Implementation Challenges

| Challenge | Description | Mitigation |
|-----------|-------------|------------|
| **Noise/False positives** | Thousands of low-value alerts | Tune rules, use risk scoring |
| **Log volume** | Petabytes of data | Tiered storage, filtering at source |
| **Skills gap** | Need specialized query languages (SPL, KQL) | Training, managed SIEM |
| **Cost** | Expensive licensing and storage | Open source options (ELK), cloud SIEM |
| **Latency** | Slow search on large datasets | Use hot/warm/cold tiers, indexing |

### Popular SIEM Products

| **Mid-Market** | Elastic Security (ELK), Exabeam, Sumo Logic, Securonix |
| **Open Source** | Wazuh, OSSIM (AlienVault), Graylog |
| **Cloud-Native** | Microsoft Sentinel, Google Chronicle, AWS Security Hub |

## 3. What is an Event, Incident, and Log?

Understanding these three terms is **fundamental to SOC operations**.

### Definitions

| Term | Definition | Analogy |
|------|------------|---------|
| **Log** | A recorded entry of something that happened | A single page in a diary |
| **Event** | Any observable occurrence in a system or network | A sentence on that diary page |
| **Incident** | An event that violates security policy or poses a threat | A diary entry saying "my house was broken into" |

### The Hierarchy

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    LOG → EVENT → INCIDENT HIERARCHY                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   LOGS (Raw data)                                                          │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  [2025-01-15 14:32:11] 192.168.1.100 → 10.0.0.50 | port 443 | ALLOW │   │
│   │  [2025-01-15 14:32:15] User:jsmith | Login FAILED | Source:10.0.0.2 │   │
│   │  [2025-01-15 14:32:18] User:jsmith | Login SUCCESS | Source:10.0.0.2│   │
│   │  [2025-01-15 14:35:00] Process: PowerShell | Created: malicious.ps1 │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                      │                                      │
│                                      ▼                                      │
│   EVENTS (Observable occurrences)                                           │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  • Failed login for user jsmith                                     │   │
│   │  • Successful login for user jsmith                                 │   │
│   │  • PowerShell script execution                                      │   │
│   │  • Outbound HTTPS connection                                        │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                      │                                      │
│                                      ▼                                      │
│   INCIDENT (Security violation)                                             │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  • jsmith's account compromised (failed→success + malicious script) │   │
│   │  • Lateral movement detected from jsmith's workstation              │   │
│   │  • Data exfiltration in progress                                    │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Detailed Breakdown

#### Logs
- **Definition:** Atomic, unprocessed records of system activity
- **Characteristics:** Immutable (once written, shouldn't change), timestamped, sourced from a specific system
- **Format:** Can be structured (JSON, CEF), semi-structured (syslog), or unstructured (text)
- **Retention:** Often retained for months/years for compliance and forensics

```
# Example: Windows Event Log (Security log)
Log Name: Security
Source: Microsoft-Windows-Security-Auditing
Event ID: 4625
Level: Information
Message: Account failed to log on. Subject: Security ID: DOMAIN\jsmith
```

#### Events
- **Definition:** A specific occurrence of interest within logs
- **Characteristics:** Every incident contains events, but not every event is an incident
- **Categories:**
  - **Normal events** (user login, file access) → Baseline
  - **Notable events** (failed login, privilege change) → Potential threats
  - **Critical events** (malware detection, admin takeover) → Almost always incidents

#### Incidents

**Definition:** A violation or imminent threat of violation of security policies, acceptable use policies, or standard security practices.

**NIST SP 800-61 Incident Categories:**

| Category | Description | Example |
|----------|-------------|---------|
| **Denial of Service (DoS)** | Resource exhaustion | DDoS attack on web server |
| **Malicious Code** | Virus, worm, Trojan, ransomware | Cryptolocker encryption |
| **Unauthorized Access** | Access without permission | Hacker in database server |
| **Inappropriate Usage** | Policy violation | Employee downloading torrents at work |
| **Multi-vector** | Combination of above | Phishing → malware → ransomware |

### Incident Severity Levels

| Level | Name | Description | Response Time |
|-------|------|-------------|---------------|
| **SEV-1** | Critical | Active breach, data loss confirmed | Immediate (<15 min) |
| **SEV-2** | High | Suspicious activity, likely compromise | <1 hour |
| **SEV-3** | Medium | Policy violation, no confirmed breach | <4 hours |
| **SEV-4** | Low | Single failed login, false positive likely | Next business day |

### The SOC Workflow: Log → Event → Incident

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    SOC ANALYST WORKFLOW                                     │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   STEP 1: COLLECT LOGS                                                     │
│   │                                                                         │
│   ▼                                                                         │
│   STEP 2: SIEM CORRELATION (Event detected)                                │
│   │   "10 failed logins from IP 5.5.5.5 to critical server"               │
│   │                                                                         │
│   ▼                                                                         │
│   STEP 3: TRIAGE (Is this an incident?)                                    │
│   │   • Is IP internal or external? External                              │
│   │   • Is the server internet-facing? Yes                                │
│   │   • Are any of those logins successful? No                            │
│   │                                                                         │
│   ├──► If NO → False positive or noise (close event)                       │
│   │                                                                         │
│   ▼                                                                         │
│   STEP 4: INCIDENT DECLARED                                                 │
│   │   "External brute force attempt against critical server"              │
│   │                                                                         │
│   ▼                                                                         │
│   STEP 5: RESPONSE                                                          │
│   │   • Block source IP at firewall                                        │
│   │   • Ensure account lockout policy is enabled                           │
│   │   • Create ticket for investigation                                    │
│   │                                                                         │
│   ▼                                                                         │
│   STEP 6: CLOSE & DOCUMENT                                                  │
│       • Document actions taken                                             │
│       • Update metrics (MTTD, MTTR)                                        │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Key Distinction: Event vs Incident

| Aspect | Event | Incident |
|--------|-------|----------|
| **Nature** | Observable | Harmful/violation |
| **Response required?** | No (generally) | Yes |
| **Example** | User lockout after 3 failed attempts | Successful brute force after 50 attempts |
| **Requires investigation?** | Rarely | Always |
| **Reported to management?** | No | Yes |

## 4. Endpoint Detection and Response (EDR)

### What is EDR?

**Endpoint Detection and Response (EDR)** is a security solution that **continuously monitors endpoint activities** (workstations, servers, laptops, mobile devices) to detect, investigate, and respond to threats in real-time.

### EDR vs Traditional Antivirus

| Feature | Traditional AV | EDR |
|---------|----------------|-----|
| **Detection method** | Signature-based | Behavioral + ML + signatures |
| **Visibility** | File scans only | Full process tree, registry, network, memory |
| **Response** | Quarantine/delete file | Isolate, kill process, rollback, forensic capture |
| **Threat hunting** | No | Yes |
| **Root cause analysis** | Limited | Full timeline |
| **Post-execution protection** | Minimal | Yes (detects malware after it runs) |

### EDR Core Capabilities


### Detection Techniques in EDR

| Technique | Description | Example |
|-----------|-------------|---------|
| **Process Parenting** | Analyzes parent-child relationships | `winword.exe` spawning `powershell.exe` (suspicious) |
| **Command Line Analysis** | Inspects executed commands | `powershell -enc SQBFAFgA...` (encoded command) |
| **MITRE ATT&CK Mapping** | Maps behaviors to attack techniques | T1059.001 (PowerShell) |
| **IOC Matching** | Compares against known bad hashes/IPs/domains | Hash matches known ransomware |
| **Anomaly Detection** | Flags deviation from baseline | Process runs from Temp folder (rare) |
| **Memory Scanning** | Scans RAM for malicious patterns | Shellcode injection detection |

### EDR Response Actions

| Action | Description | Use Case |
|--------|-------------|----------|
| **Kill Process** | Terminate malicious process | Active malware running |
| **Quarantine File** | Isolate file, prevent execution | Suspicious executable |
| **Isolate Endpoint** | Cut network access (except EDR) | Confirmed compromised host |
| **Rollback** | Revert file changes | Ransomware file encryption |
| **Forensic Capture** | Collect memory/disk image | Investigation evidence |
| **Run Script** | Execute custom remediation | Cleanup or hunting |

### Example: Ransomware Detection in EDR

```
TIMELINE OF DETECTION:

14:32:10 - Process created: word.exe (PID 1234)
14:32:15 - word.exe spawned powershell.exe (PID 5678)  ← ANOMALY (Office spawning shell)
14:32:16 - powershell.exe downloaded file from suspicious domain
14:32:18 - Downloaded file executed (ransomware.exe)
14:32:20 - ransomware.exe begins encrypting .docx, .xlsx files
14:32:21 - EDR detects file encryption behavior (behavioral rule)
14:32:21 - EDR alerts SOC, automatically isolates endpoint
14:32:25 - Analyst reviews, approves kill process and rollback

Result: Encryption stopped after ~5 seconds (limited damage)
```

## 5. Extended Detection and Response (XDR)

### What is XDR?

**Extended Detection and Response (XDR)** is a unified security platform that **integrates and correlates data across multiple security layers**—endpoints, networks, cloud, identity, and email—to provide a holistic view of threats.

### The XDR Value Proposition (Why XDR?)

**Problem:** Security teams have 20+ tools producing siloed alerts. Analysts manually correlate across them.

**Solution:** XDR connects the dots automatically.

**Example Cross-Layer Detection:**

| Alert Source | Alert Content |
|--------------|---------------|
| Email Gateway | User clicked link in phishing email |
| Endpoint (EDR) | PowerShell downloaded suspicious script |
| Network Firewall | Outbound connection to known C2 IP |
| Identity | Privilege escalation to Domain Admin |

**XDR Correlation:** Connects all 4 alerts into a **single incident**—"Phishing → Compromise → C2 → Privilege Escalation"

### XDR Response Orchestration

With XDR, a **single response action** can coordinate across multiple products:

```
Analyst clicks "Isolate User" in XDR console:

XDR automatically:
├─ Isolates user's endpoint (EDR)
├─ Blocks user's IP at firewall (Network)
├─ Revokes user's sessions (Identity/AD)
├─ Quarantines malicious email (Email Gateway)
└─ Alerts cloud security team (Cloud)
```

### XDR Benefits vs Challenges

| Benefits | Challenges |
|----------|------------|
| Faster detection (correlated alerts) | Vendor lock-in (works best with own products) |
| Reduced analyst workload (no manual correlation) | Expensive (premium pricing) |
| Single-pane-of-glass visibility | Limited to vendor's telemetry sources |
| Unified response actions | SIEM still needed for compliance/long-term |
| Better detection of multi-stage attacks | Implementation complexity |

## 6. User Entity Behavior Analytics (UEBA)

### What is UEBA?

**User and Entity Behavior Analytics (UEBA)** uses **machine learning and statistical modeling** to establish baselines of normal behavior for users and entities (servers, applications, devices), then detects **anomalies** that may indicate threats.

### Key Concept

> *"Instead of looking for known bad (signatures), UEBA looks for unusual good."*

### Types of Entities Analyzed

| Entity Type | Examples | Behavioral Metrics |
|-------------|----------|---------------------|
| **Users** | Employees, contractors, service accounts | Login times, data access, application usage, geolocation |
| **Endpoints** | Workstations, servers, laptops | Process execution, network connections, file access |
| **Network Devices** | Firewalls, routers, switches | Configuration changes, traffic patterns, admin logins |
| **Cloud Resources** | S3 buckets, VMs, databases | API calls, access patterns, data transfer volumes |
| **Applications** | Salesforce, Office 365, Workday | Login frequency, data export, privilege changes |

### Common UEBA Use Cases & Anomalies

| Use Case | Anomaly Detected | Risk Indicator |
|----------|------------------|----------------|
| **Insider Threat** | User accesses 500+ files (normally accesses 10) | Data theft prep |
| **Account Compromise** | Login from new country (never traveled) | Credential misuse |
| **Privilege Abuse** | Admin creates account at 3 AM (normally 9-5) | Malicious insider |
| **Lateral Movement** | User logs into 5 workstations in 2 min | Attack spreading |
| **Data Exfiltration** | User downloads entire database (normally queries only) | Data theft |
| **After-hours activity** | User active on VPN every night (normally never) | Possible compromise |
| **Service Account Misuse** | Service account used for interactive login | Abuse of privileged account |
| **Mimikatz-like behavior** | Process accessing LSASS memory | Credential dumping |

### Peer Group Analysis (Key UEBA Technique)

Instead of comparing a user only to their own history, UEBA compares them to **similar users** (same department, role, location).

**Example:**
- User in Finance normally exports 10 reports/month
- Same user exports 20 reports in one day → Anomaly (vs self)
- **But** if ALL Finance users are exporting 20 reports today → Not anomaly (quarterly reporting)

### Example: UEBA Detection in Action

```
SCENARIO: Compromised Marketing Manager Account

Baseline (30 days):
├─ Login times: 8:30 AM - 6:00 PM (weekdays)
├─ Login location: Chicago office (IP range 192.168.1.x)
├─ Data access: 20-30 files/day (mostly marketing collateral)
├─ VPN: Only when traveling (1-2 days/month)

ANOMALY DETECTED:
├─ Login at 2:15 AM (Tuesday) → +2.5 standard deviations from baseline
├─ Login from Russia (IP 5.5.5.5) → New country
├─ Accessing HR files → Never accessed before (new resource type)
├─ Downloaded 200 files in 5 minutes → +10x normal velocity

UEBA RISK SCORE: 98/100 → CRITICAL ALERT

SOC ACTION: Immediately isolate endpoint, reset password, investigate
```

### UEBA vs Traditional Rules

| Aspect | Rule-Based (SIEM) | UEBA |
|--------|-------------------|------|
| **Approach** | Static thresholds | Dynamic baselines |
| **Adaptability** | Requires manual tuning | Adapts automatically |
| **Known threats** | Excellent | Moderate |
| **Unknown threats** | Misses | Detects |
| **False positives** | High (if threshold low) | Lower (context-aware) |
| **Insider threats** | Weak | Strong |

| **Integrated in SIEM** | Splunk UEBA, IBM QRadar UBA, Microsoft Sentinel |
| **Integrated in XDR** | Palo Alto Cortex XDR, CrowdStrike Falcon Insight |

## 7. Security Orchestration, Automation, and Response (SOAR)

### What is SOAR?

**SOAR (Security Orchestration, Automation, and Response)** is a platform that **connects security tools, automates workflows, and manages incident response** to improve efficiency and reduce manual work.

### The Three Components of SOAR

| Component | Description |
|-----------|-------------|
| **Orchestration** | Connects different security tools and systems to work together |
| **Automation** | Executes repetitive tasks without human intervention |
| **Response** | Manages incident lifecycle from detection to closure |

### Why SOAR? (The Problem SOAR Solves)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    PROBLEM: ALERT VOLUME vs ANALYST TIME                    │
├─────────────────────────────────────────────────────────────────────────────┤

│   Typical SOC receives 5,000+ alerts per day                               │
│   Analysts can manually investigate ~10-20 alerts/day                      │
│                                                                             │
│   RESULT:                                                                   │
│   • 90%+ alerts never investigated                                         │
│   • Analyst burnout from repetitive tasks                                  │
│   • Slow response (manual processes)                                       │
│   • Inconsistent handling                                                  │
│                                                                             │
│   SOAR SOLUTION: Automate 80% of repetitive work                           │
│   • Analysts focus on 20% of alerts that need human judgment              │
│   • Response time: Hours → Minutes                                         │

```

```
│        ▼                                                                    │

│        │                                                                    │
│        ▼                                                                    │
│   STEP 2: ENRICH INDICATORS                                                │

│        │                                                                    │
│        ▼                                                                    │

│   IF indicators are MALICIOUS:                                             │
│        ├─ Create HIGH severity incident                                    │
│        ├─ Block sender domain at email gateway                             │
│        ├─ Block malicious URLs at proxy                                    │
│        ├─ Search EDR for any endpoint that clicked link                    │
│        │     │                                                             │
```
